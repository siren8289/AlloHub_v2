# 출자배분계산 코드검증

- 범위: ALH-0220 ~ ALH-0319, ALH-0882, ALH-0883 (102건)
- 대상: `back/src/main/java/com/allohub/allocation/AllocationCalculator.java`. ALH-0882·ALH-0883은 `AllocationService`의 합 허용오차와 `InvestorRequest`·`AllocationRequest` 검증을 같이 본다.
- 방법: `AllocationCalculator.split`을 javac로 직접 호출해 100건 기대 금액과 대조했다. 기존 JUnit은 `./gradlew test --tests com.allohub.allocation.AllocationCalculatorTest`가 BUILD SUCCESSFUL이다. 그 클래스는 33.33 분할과 60/40만 단언한다.
- 판정: 통과 100, 실패 2, 부분 0, 확인불가 0

## 실패·부분

- ALH-0882 실패. `split(100, [100.0, 0.01])` 재현 값은 `[100, 0]`, 합 100, 음수는 아니다. 앞 출자자는 100%라 `100×100/100`을 `RoundingMode.DOWN`하면 100이다. 0.01% 출자자는 마지막이라 자기 비율(정확값 0.01원)을 쓰지 않고 잔액 `100-100=0`만 받는다. 서비스 합 검사는 `Math.abs(ratioSum-100) > 0.05`이고, Java double 합은 100.01, 절대차 약 0.01이라 400이 아니다. 최소 금액은 `AllocationRequest.totalAmount`의 `@Min(1)`뿐이고, 줄 금액에는 하한이 없다. `InvestorRequest`의 `@DecimalMin("0.01")`은 비율이 0보다 커야 한다는 조건인데, 그 비율이 그대로 0원이 된다. 요구가 충돌하고 0원 방어는 없다. 합이 총액과 같아 `balanced`는 true다.
- ALH-0883 실패. `split(100, [50, 50, 0.01])` 재현 값은 `[50, 50, 0]`, 합 100. 앞 둘은 비마지막이라 DOWN 절사가 각 50이고, 그 부분합은 100으로 100%를 넘지 않은 채 총액을 다 쓴다. 세 비율을 모두 더한 합은 100.01이라 100%를 넘지만 절대차 약 0.01로 허용오차 안이라 서비스가 거절하지 않는다. 마지막 0.01%는 비율 곱을 건너뛰고 잔액 0원이다. 0원·음수 방어가 없다.

## 재현

- 알고리즘: 비마지막은 `BigDecimal.valueOf(total).multiply(BigDecimal.valueOf(ratio)).divide(100, 0, RoundingMode.DOWN)`, 마지막은 `totalAmount - used`. 합은 이 잔액 조정 때문에 총액과 같다. 0 미만으로 내리는 보정은 없다.
- ALH-0220~ALH-0319 100건은 위 구현의 재현 금액이 기대 `amounts`와 같고, 합은 총액이며, 음수는 없다.
- 같은 잔액식은 허용오차 안에서도 음수가 된다. Java로 확인한 예: 총액 10000, 비율 `[0.01, 100.0, 0.01]`, double 합 약 100.02라 `> 0.05`가 아니고, `split` 결과는 `[1, 10000, -1]`, 금액 합 10000. ALH-0883 자체 결과는 음수가 아니라 0이다.
- `AllocationCalculatorTest.lastInvestorTakesRemainder`는 총액 100, `[33.33, 33.33, 33.34]` → `[33, 33, 34]`로 ALH-0273과 같다.
