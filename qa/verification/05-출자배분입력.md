# 출자배분입력 코드검증

- 범위: ALH-0081 ~ ALH-0141, ALH-0884 (62건)
- 대상: `front/src/pages/AllocatePage.tsx`, `front/src/api/api.ts`, `back/src/main/java/com/allohub/allocation/dto/AllocationRequest.java`, `back/src/main/java/com/allohub/allocation/dto/InvestorRequest.java`, `back/src/main/java/com/allohub/allocation/controller/AllocationController.java`, `back/src/main/java/com/allohub/allocation/service/AllocationService.java`, `back/src/main/java/com/allohub/allocation/entity/AllocationLine.java`, `back/src/main/java/com/allohub/global/exception/GlobalExceptionHandler.java`
- 방법: 소스 대조. 브라우저 실행 없음. 금액은 `Number`와 `JSON.stringify`를 재현하고, Jackson 2.15 기본 `ObjectMapper`로 `Long` 역직렬화를 확인했다.
- 판정: 통과 49, 실패 7, 부분 6, 확인불가 0

## 실패·부분

- ALH-0093 실패. 배분 실패 시 이전 `result`를 지우지 않는다. 오류 문구 아래에 지난 성공 카드가 남는다.
- ALH-0106 실패. `1.5`는 화면을 통과하고 Jackson이 `Long` 1로 잘라 `@Min(1)` 저장까지 된다. 1.5원 거부도, 소수 안내도 없다.
- ALH-0107 실패. `1e3`은 1000원으로 조용히 저장된다. 지수 표기 거부나 안내가 없다.
- ALH-0111 실패. `9007199254740992`는 JS에서 그 값 그대로라 정밀도는 깨지지 않는다. 그러나 화면과 `@Min(1)` 모두 상한이 없어 안전정수 경계 금액을 거부하지 않고 저장한다.
- ALH-0113 실패. ` 100 `은 100원으로 조용히 저장된다. 공백 입력 오류가 없다.
- ALH-0118 부분. 비율 0은 합계에 반영되고, 합이 100이면 화면이 보낸다. 저장은 서버 `@DecimalMin("0.01")` 400으로만 막힌다.
- ALH-0119 부분. `-0.01`도 화면 범위 검사가 없다. 합이 100이면 제출되고 서버 최소값 400이 저장을 막는다.
- ALH-0120 부분. `100.01`은 100과의 차이가 0.05 이하라 화면 합계 검사를 통과한다. 서버 `@DecimalMax("100")`만 400으로 막는다.
- ALH-0123 부분. 빈 비율은 `Number("")===0`이라 0과 같다. 화면은 빈 값을 거절하지 않고, 서버 최소값 400이 저장을 막는다.
- ALH-0124 부분. `abc`는 NaN이라 합계에서 0으로 세고, 합이 100이면 `ratio: null`로 제출된다. 서버 `@NotNull` 400으로 저장은 안 된다. 화면의 숫자 검증은 없다.
- ALH-0125 부분. `NaN` 문자열도 ALH-0124와 같다. 저장은 서버 null 거절로 막히고, 화면은 NaN을 0처럼 합친다.
- ALH-0139 실패. 512자 이름에 `@Size`가 없다. 기본 255자 컬럼에서 깨지면 500 `서버 오류가 발생했습니다.`만 나온다.
- ALH-0884 실패. `9007199254740993`은 `Number` 이후 `9007199254740992`가 된다. UI는 거부하지 않고 서버는 그 틀린 Long을 저장한다.
