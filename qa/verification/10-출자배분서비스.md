# 출자배분서비스 코드검증

- 범위: ALH-0320 ~ ALH-0337 (18건)
- 대상: `AllocationService`, `AllocationController`의 `@Valid`, `AllocationRequest`, `InvestorRequest`, `GlobalExceptionHandler`, `Allocation`·`AllocationLine`
- 방법: 저장·검증 순서는 소스를 대조했다. 비율 합의 `>` 비교와 `AllocationCalculator.split`은 Java 17에서 입력 double로 재현했다. 서비스 MockMvc는 다시 돌리지 않았다. 계산기 JUnit은 `./gradlew test --tests com.allohub.allocation.AllocationCalculatorTest`가 BUILD SUCCESSFUL이다.
- 판정: 통과 13, 실패 2, 부분 3, 확인불가 0

## 실패·부분

- ALH-0320 실패. 비율 `[100.0, 0.01]`, 총액 1000. Java double 합은 100.01이고 `Math.abs(sum-100) > 0.05`는 false라 400이 아니다. `split` 재현은 `[1000, 0]`, 합 1000. 앞 100%는 DOWN으로 1000, 마지막 0.01%의 정확값 0.1원은 쓰이지 않고 잔액이 0이다. 줄 금액 최소가 없어 비율 최소 0.01과 충돌한다. 합이 총액과 같아 `balanced`는 true다.
- ALH-0322 부분. `[50, 49.96]`, 총액 1000. 절대차 약 0.04로 `> 0.05`가 아니라 허용된다. 재현 `[500, 500]`. 둘째 정확값은 499.6원인데 마지막 잔액이 500원이라 낸 비율 49.96%와 금액 비율 50%가 0.4원 어긋난다. 합계만 맞추고 비율로 다시 나누지 않는다.
- ALH-0323 부분. `[60, 40.04]`, 총액 1000. 절대차 약 0.04로 허용. 재현 `[600, 400]`. 둘째 정확값 400.4원보다 잔액이 0.4원 적다. 합은 1000이다.
- ALH-0324 부분. `[30, 30, 39.95]`, 총액 1000. double 절대차는 약 0.049999999999997이라 0.05보다 크지 않고, 비교가 `>`라 경계 0.05도 거절되지 않는다. 재현 `[300, 300, 400]`. 셋째 정확값 399.5원 대신 잔액 400원이다. 합은 1000이다.
- ALH-0335 실패. `cut`은 `length()`와 `substring(0, 2000)`이라 UTF-16 코드유닛이다. 재현: 한글 1999자 뒤에 이모지(서로게이트 쌍)를 붙이면 길이 2001, 자른 뒤 길이 2000, 마지막 문자는 high surrogate다. 이모지가 깨지고 뒤 내용은 잘린다.

## 재현

- 합 게이트는 `allocate`에서 AI 호출 전에 `Math.abs(ratioSum - 100.0) > 0.05`이면 `ApiException.badRequest`다. 같거나 더 작은 차는 통과다.
- 허용되면 비마지막은 `total*ratio/100`을 `RoundingMode.DOWN`, 마지막은 `total-used`다. 마지막 비율은 금액 계산에 들어가지 않는다.
- ALH-0321만 거절된다. `50+49.94`의 절대차는 약 0.060000000000002로 0.05보다 크다.
